## First setup step: name the project after its domain

- For every authorized new website, the first setup action after reading the rules
  and confirming the exact domain is to create the working copy in a folder named
  exactly after that domain: `valoranthacks.com/`, not `zadeyo-template/`,
  `new-site/` or the previous game's name. Use the domain without scheme or path.
- Preserve the reusable master. If a fresh working copy still has a generic template
  name, rename that copy before editing its website content. Inspect any existing
  destination first; never overwrite or merge another site's folder silently.
- Keep each converted site's `AGENTS.md`, a copy of `PROJECT_RULES.md` and
  `START_HERE.md` in its own root so its rules travel with it. Its `AGENTS.md` must
  point to its local rules, not rely solely on a parent folder or this chat.
- Align the site origin, public identity and hosting configuration with the supplied
  domain during conversion; folder naming alone does not rebrand the website.
- A rules-only request does not rename the master or start a website conversion.

## Audit and conversion sequence

Use the four-part execution order below for new sites. The detailed audit list
after it describes coverage, not an instruction to translate before English is final.

### Part 1: setup, audit and actual English commercial rewrite

- Read the rules, set up the exact-domain working folder, audit source/assets/output
  and record the layout baseline and former-game fingerprints. Discover available
  relevant skills; do not claim unavailable conversion skills were used.
- Research confirmed game/product facts and run `content:prepare` before changing
  the origin. Record commercial keyword/URL ownership; editorial topics remain
  provisional until the supplied competitor URLs are read in Part 2.
- Write and integrate new English copy in the actual homepage, product, catalog,
  FAQ, about/support, relevant legal/identity and hub fields, including metadata and
  schema descriptions. Config edits, a game-name replacement, article titles or a
  content plan alone never count as a content conversion.
- Report the routes/source fields actually rewritten. Then request the new game
  images; images are not a prerequisite for rewriting verified English copy.

### Part 2: images, original English blogs and forums with editorial answers

- Apply the supplied game artwork to existing placements; preserve approved utility
  art and the layout. After the image step, obtain/read the competitor article URLs
  and relevant Cloud DMA references. If fields are already filled, use them directly.
- Use those URLs to research topics and gaps, then write full original game-specific
  articles, not copied/closely paraphrased text or renamed old articles. Independently
  research utility topics without supplied URLs. Revalidate the content plan when
  topics/slugs change, update `pack.planHash` and re-review affected drafts while
  preserving still-valid copy; write articles in small completed batches.
- Create game-specific forum topics and substantive publisher-written answers in
  the existing comment presentation. Clearly label these as editorial answers with
  truthful brand authorship; never impersonate customers or invent community activity.
  Use real supplied comments only with accurate provenance and authorization.
- The template's baseline pack currently rejects all generated comments. During the
  authorized conversion, deliberately extend its types, pack contract, renderer,
  schema and validation to support labeled editorial answers, with focused regression
  checks. Do not disable guards, fake review flags or silently omit requested answers.
  Keep votes zero and any displayed answer count equal to actual editorial answers;
  do not represent these as customer engagement or fabricate review/rating schema.
- Report full article/topic/answer counts, titles/slugs and source/draft locations.
  Complete checked integration and rendered verification after translations in Part 3.

### Part 3: cleanup, final English URLs/links, then complete translations

- Remove obsolete products, old-game source/copy/media, links, checkout aliases,
  redirects and generated paths; retain only explicitly non-public provenance that
  the content gate needs. Repair URL slugs, intent ownership, contextual internal
  links, hub/product relationships, breadcrumbs, RSS and routing consistently.
- Settle and review English page/article bodies, routes and links before translating.
  Keep shared slugs across languages; do not create an unnecessary localized slug system.
- Translate everything into Spanish, German and French: commercial prose, complete
  blogs, forum topics/answers/disclosures, UI, metadata, schema text, alt text and link
  labels. Adapt wording naturally; preserve verified facts, prices and destinations.
  Check each language for English fallback and former-game residue.
- Respect the existing all-locale content gate: keep incomplete work marked WIP,
  leave origin switching/final install until the complete pack is ready, then check
  the pack, configure the target identity/origin and install it. Do not bypass the
  manifest requirement to make a partial conversion build. Reconcile native English
  edits with the final approved pack before installing.
- Build and inspect all four languages; verify rewritten paragraphs/article bodies
  appear in rendered pages. A correct title or empty route is not completion evidence.

### Part 4: theme, mobile, desktop and final SEO/crawl checks

- Repair light-theme colors/contrast, controls, persistence and initial flashes while
  preserving the existing layout and dark/purple/white identity. Then fix mobile
  behavior/performance before desktop performance; do not remove content/features
  or change section order to improve a score.
- Finish technical and on-page SEO; finalize one multilingual sitemap, robots,
  canonicals, hreflang, schema, crawlability and indexability as technical SEO work.
- Target Lighthouse SEO 100/100 and Seobility's applicable on-page/technical checks
  at 100%; record actual tool scores and remaining findings. Also measure mobile and
  desktop performance and fix actionable bottlenecks. A score is not proof of perfect
  SEO. Never invent a Screaming Frog score; use its crawl inventory and issue exports.
- Use real available Lighthouse, Seobility and Screaming Frog checks. Record the URL,
  revision/build, tool/version, settings, date, results and report paths. Seobility or
  other remote checks need a reachable authorized target or supplied report; do not
  deploy/tunnel a private site just to obtain a score. Mark unavailable or partial
  checks NOT TESTED/PARTIAL with reasons, complete independent local checks and report
  exactly what remains before claiming full external verification.
- Keep local crawls bound to the working site and intercept/exclude purchase redirects.
  Compare production canonical/hreflang/sitemap destinations against the intended
  domain without rewriting them to localhost or contacting checkout to pass an audit.
- Sitemaps and internal links are not off-page SEO. The owner's no-backlink policy
  remains: no unsolicited outreach, submissions, link buying or fabricated authority.
  Record externally dependent findings separately; push/deploy/index only if requested.
- Run final required repository checks, source/output residue scans and layout/browser
  review; refresh localhost and deliver actual evidence. Each part updates
  `PROJECT_STATUS.md` and finishes its whole scope before the next prompt.

## Locale, sitemap and architecture rules

- Retain **en, es, de, fr**. English routes are unprefixed; others use `/es/`,
  `/de/`, `/fr/`. Preserve consistent trailing slashes and translated content.
- One **`/sitemap.xml`** contains every indexable canonical URL in all four languages.
  Do not publish separate per-language sitemaps or a sitemap index for these sites.
- Include each URL's self-reference and reciprocal en/es/de/fr `xhtml:link`
  alternates, plus `x-default` pointing to English. Include all four HTML head
  alternates in server-generated source on corresponding indexable pages.
- Include page priorities as requested. They express the chosen site hierarchy;
  Google ignores `<priority>` and `<changefreq>` and they do not set regional rank.
- Keep each translated page self-canonical; never canonicalize all locales to English.
- Include only canonical indexable URLs in the sitemap. Exclude checkout redirects,
  error pages and intentional noindex pages. Use truthful lastmod dates.
- Maintain navigation -> catalog -> product, and blog hub -> article discovery;
  connect each article contextually to the relevant product and related articles.
- Use descriptive natural anchors, localized destinations, useful breadcrumbs and
  valid related-content references. Check broken links, redirect hops, orphans,
  duplicated intents and keyword cannibalization.
